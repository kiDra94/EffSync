# Thesis Alignment Audit – EffSync

Audit date: 2026-11-06 (branch `development`, commit `e484b02`). Companion to [GOALS.md](GOALS.md) and [UNUSED_CODE.md](UNUSED_CODE.md).

**Scope.**
- **Read:** the thesis as built by `thesis/main.tex`. That is chapters `01`–`11` and `Anhang` (which inputs `usability_test.tex` and `prisma_schema.tex`).
- **Not part of the build:** `Abstract.tex` is not included by `main.tex`. Its claims repeat chapters 2 and 9 and are not listed separately.
- **Stale duplicate:** `04_DigitalerWorkflosMitGithub.tex` is not included (see UNUSED_CODE.md).
- **Prisma schema:** the listing in `thesis/content/prisma_schema.tex` is **identical** to `backend/prisma/schema.prisma` (compared model by model). The schema is therefore part of what the thesis documents.

**Rules applied.**
- Per the decisions in GOALS.md, the thesis is the source of truth. Wherever a claim is Partial, Missing or Contradicted, the code is changed. The thesis is read-only.
- Thesis references are `file:line`, with paths relative to `thesis/content/`. Code references are relative to `backend/src/` or `frontend/src/` unless a longer path is given.
- Coverage numbers come from `jest --coverage` and `vitest run --coverage` on 2026-11-06.
- Statuses:
  - **Implemented:** the code matches.
  - **Partial:** the feature exists but differs from the thesis.
  - **Missing:** not in the code.
  - **Contradicted:** the code does something different.
  - **Ambiguous:** the passage allows more than one reading. Each one is listed under Open questions in GOALS.md.
  - **Deferred:** out of scope for this refactor by a recorded decision (Decisions log in GOALS.md). Currently this means the company version (decision Q1, F11) and claims that can only be verified in production operation (decision Q4, F1). Deferred claims don't count against the Definition of done.

## 2. Lessons learned (refactoring targets)

| ID | Thesis reference | What it asks for |
|---|---|---|
| L1 | `11_Reflexion.tex:25-31`; `10_Ausblicke.tex:5-9` | **Replace the Table-Module pattern with a domain-driven architecture.** `11_…:27` says the table-per-module approach caused architectural weaknesses across the system. `11_…:29` names the concrete symptom: task create/update/delete must also write `task_activity_log`, but because these operations are spread over separate modules and controllers they don't run as one atomic transaction, so a failed log write after a successful task update leaves inconsistent data. `11_…:31` says a DDD-based approach would have been the better alternative for the **whole backend**: modules organized by business domains and processes instead of tables. It continues: one `TaskController` responsible for all task operations, including activity-log maintenance in one shared transaction; task management as its own **bounded context**, in which the `TaskController` acts as **aggregate root** and encapsulates all consistency rules; responsibilities separated by the Single Responsibility Principle. `10_…:7` makes this the next refactoring step ("strikt entlang von Domänengrenzen"), and `10_…:9` adds that **task comments and the activity log** belong in that same task domain and central `TaskController`. Decision Q6: "aggregate root" is read in its DDD sense: the `Task` aggregate lives in `domain/`, and `TaskController` is the single HTTP entry point with task-scoped routes |
| L2 | `11_Reflexion.tex:11`; `11_Reflexion.tex:38` | Tests should come earlier: automated tests written only after implementation caused extra bug-fix loops, and test-driven development would have caught problems earlier. Target: every milestone writes or updates tests **before** changing code (characterization tests before refactoring, failing tests before fixing a thesis claim) |

Not refactoring targets:
- `11_Reflexion.tex:13-23` compares in-place anonymization with the ghost user and keeps the ghost user. That is a design rationale; T10 implements the ghost-user approach.
- `11_Reflexion.tex:34-40` is about personal time management.
