# Secrets Managment und HTTPS-Vorgaben

## Kommunikationssicherheit und Header-Management
Da EffSync als entkoppelte Architektur operiert, muss die Kommunikation zwischen dem Vue.js-Frontend und dem NestJS-Backend abgesichert werden.

### HTTPS-Konzept in der Produktion (Note: In Planung wird später noch definiert, falls wir es anders deployen!!!)
Während in der lokalen Entwicklungsumgebung auf SSL verzichtet wird, ist für den Produktivbetrieb ein **HTTPS-Erzwingungskonzept** vorgesehen. Die TLS-Terminierung erfolgt hierbei über einen [**Nginx Reverse Proxy**](https://docs.nginx.com/nginx/admin-guide/security-controls/terminating-ssl-http/) in Verbindung mit automatisierten **Let's Encrypt**-Zertifikaten. Der über Helmet gesetzte `Strict-Transport-Security`-Header (HSTS) stellt sicher, dass Browser zukünftig ausschließlich verschlüsselte Verbindungen zur EffSync-Instanz aufbauen.

## Strategie für Secrets-Management und Umgebungsvariablen
Ein zentraler Aspekt der Sicherheit ist die strikte Trennung von Programmcode und sensiblen Zugangsdaten gemäß den Prinzipien der [**12-Factor-App**](https://12factor.net/config).

### Umgebungsvariablen (.env-Strategie)
EffSync nutzt ein differenziertes System zur Verwaltung von Konfigurationen:
-  **Lokale Entwicklung:** Secrets werden in lokalen `.env`-Dateien gespeichert, die über die `.gitignore`-Konfiguration strikt vom Versionskontrollsystem ausgeschlossen sind.
-  **Dokumentation:** Im Repository werden ausschließlich `.env.example`-Dateien mit Platzhaltern bereitgestellt, um die benötigte Struktur ohne Offenlegung von Credentials zu dokumentieren.
```
# JWT Authentication
JWT_SECRET="your-super-secret-jwt-key-change-this-in-production"
JWT_EXPIRATION="7d"
JWT_REFRESH_EXPIRATION="30d"

# Server Configuration
PORT=3000
NODE_ENV=development

# Frontend Configuration (CORS)
FRONTEND_URL="your-frontend-url"
ALLOWED_ORIGINS="first-url,second-url"
```
-  **Produktionsumgebung:** In der Produktion werden Secrets direkt als Umgebungsvariablen im Betriebssystem oder über das Deployment-Tool injiziert, um das Risiko durch auf dem Dateisystem liegende Klartext-Dateien zu minimieren.

### Alternative Ansätze zur Konfigurationsverwaltung

Ein theoretisch möglicher Ansatz zur Verwaltung sensibler Daten ist die Verwendung dedizierter Konfigurationsdateien (z. B. `config/database.yml` oder `secrets.json`), die explizit von der Versionsverwaltung ausgeschlossen werden. Obwohl diese Methode eine deutliche Verbesserung gegenüber hartcodierten Konstanten im Quellcode darstellt, weist sie in der Praxis erhebliche Schwächen auf, wobei folgende Punkte am kritischsten zu bewerten sind:

- **Risiko unbeabsichtigter Veröffentlichungen:** Bei dateibasierten Ansätzen besteht ein erhöhtes Risiko, dass sensible Dateien durch menschliches Versagen versehentlich in ein öffentliches Repository committet werden (z. B. durch eine fehlerhaft konfigurierte oder vergessene .`gitignore`-Datei).

- **„Secure-by-Default“-Vorteil von .env:** Im Gegensatz zu benutzerdefinierten Konfigurationsdateien bieten moderne Frameworks wie **NestJS** einen proaktiven Schutz. Bei der Initialisierung eines Projekts über die **NestJS-CLI** wird die `.env`-Datei [automatisch](https://github.com/nestjs/nest-cli/issues/166) in die standardmäßige `.gitignore` aufgenommen. Durch diesen „Secure-by-Default“-Ansatz wird das Risiko für menschliches Versagen minimiert, da die Sicherheitsvorkehrungen bereits systemseitig getroffen werden, bevor der erste Commit erfolgt.

### JWT-Sicherheit
Um die Sicherheit der Authentifizierung zu garantieren, wurde im `JwtStrategy`-Modul auf jegliche **Fallback-Secrets (wird noch im späteren issu noch entfernt!!)** verzichtet. Das System erzwingt die Existenz einer externen Umgebungsvariable für den kryptografischen Schlüssel. Fehlt diese Konfiguration, verweigert der Server den Start (Fail-Fast-Prinzip), anstatt auf einen unsicheren Standardwert zurückzugreifen.
