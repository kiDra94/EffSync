# Sicherheitsmaßnahmen

Um die Integrität des Gesamtsystems **EffSync (Worksync)** zu gewährleisten und das Backend gegen gängige Angriffsvektoren abzusichern, wird eine mehrschichtige Sicherheitsstrategie auf Basis von NestJS-Interceptors und Middlewares implementiert.

## Validierung der Datenschemata (Input-Validierung)

Da die App das Erstellen von Tasks, Subtasks, Chatnachrichten und ähnlichem erlaubt, könnte ohne Validierung ein Nutzer versuchen schädlichen Code in beispielweiße Task-Titel zu schreiben. Damit das verhindert wird, wird bereits beim Eintritt der Daten in das System desen Integrität sichergestellt. Hierzu werden für alle Endpunkte Data Transfer Objects (DTOs) definiert, die mittels [`class-validator`](https://github.com/typestack/class-validator)-Frameworks umgesetzt sind.

```typescript
import {
  IsInt,
  IsNotEmpty,
  IsString,
  IsOptional,
  IsEnum,
  IsDateString,
  Min,
  Max,
} from "class-validator";
import { task_status } from "@prisma/client";

export class CreateTaskDto {
  @IsString() @IsNotEmpty() title: string;
  @IsString() @IsOptional() description?: string;
  @IsEnum(task_status) @IsOptional() status?: task_status;
  @IsInt() @Min(0) @Max(100) @IsOptional() progress?: number;
  @IsString() @IsOptional() deadline?: string;
  @IsInt() @IsOptional() created_by?: number;
  @IsInt() @IsOptional() assigned_to?: number;
  @IsInt() @IsOptional() parent_task_id?: number;
  @IsInt() @IsOptional() priority_id?: number;
}
```
- **Technische Umsetzung:** Die globale Aktivierung erfolgt über die ValidationPipe in der main.ts. Dies erzwingt eine strikte Typisierung und verhindert das Einschleusen nicht definierter Felder.
```typescript
// some code
// in main.ts
app.useGlobalPipes(
    new ValidationPipe({
      whitelist: true,
      forbidNonWhitelisted: true,
      transform: true,
    }),
  );

// some code
```
- **Schutzwirkung:** Diese Maßnahme unterbindet Mass Assignment Attacks und stellt sicher, dass nur logisch konsistente Daten (z. B. korrekte Datumsformate für Deadlines oder valide Statuswerte aus Task-status) verarbeitet werden.

## Cross-Origin Resource Sharing (CORS)
Da EffSync als entkoppelte Architektur (Vue.js-Frontend und NestJS-Backend) operiert, ist eine restriktive [CORS-Policy](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS) essenziell.

- **Konfiguration:** Das Backend wird so konfiguriert, dass ausschließlich Anfragen der explizit definierten Frontend-Domain akzeptiert werden.
```typescript
// some code
// in main.ts
app.enableCors({
    origin: process.env.FRONTEND_URL || "http://localhost:5173",
    methods: "GET,HEAD,PUT,PATCH,POST,DELETE",
    credentials: true,
    allowedHeaders: ["Content-Type", "Authorization"],
  });

// some code
```
- **Begründung:** Dies verhindert, dass schädliche Skripte von Drittanbieter-Websites (`www.harmfullapp.com`) im Kontext des Nutzers Anfragen an die API senden, und schützt somit vor unautorisierten Cross-Site-Interaktionen.

## **Absicherung der HTTP-Header via Helmet**

Zur Härtung der Kommunikation auf Protokollebene wird die Middleware [Helmet](https://docs.nestjs.com/security/helmet) integriert. Diese setzt automatisch sicherheitsrelevante HTTP-Response-Header.
```typescript
// some code
// in main.ts
app.use(helmet());

// some code
```
### Warum Helemet?
[Helmet](https://helmetjs.github.io/) mit Standardkonfiguration setzt automatisch diese Header:

| Header                      | Schutz / Zweck                                   |
|-----------------------------|---------------------------------------------------|
| X-Frame-Options: SAMEORIGIN | Schutz vor Clickjacking                           |
| X-Content-Type-Options: nosniff | Verhindert MIME-Sniffing                    |
| Referrer-Policy             | Verhindert Datenleck über Referrer               |
| X-XSS-Protection: 0         | Deaktiviert veralteten Browser-XSS-Filter        |
| Content-Security-Policy (Basis) | Schutz vor XSS / Script-Injection          |
| Strict-Transport-Security (HSTS) | Erzwingt HTTPS und schützt vor Downgrade |

### Schutzwirkung:
- **Content-Security-Policy (CSP):** Verringert das Risiko von `Cross-Site Scripting (XSS)`. Bei Task-Titel, Beschreibungen, Kommentare, Chat-Nachrichten kann ohne CSP-Header eingeschleuster JavaScript-Code im Browser eines anderen Nutzers ausgeführt werden (gespeichertes XSS).

- X-Frame-Options: Verhindert Clickjacking, indem das Einbetten der Applikation in fremde iFrames untersagt wird.

- Strict-Transport-Security: Erzwingt die Kommunikation über verschlüsselte HTTPS-Verbindungen.

## **Ressourcen-Kontrolle (Rate Limiting)**

Um die Verfügbarkeit des Systems (Availability) zu garantieren, wird das [`ThrottlerModule`](https://docs.nestjs.com/security/rate-limiting#multiple-throttler-definitions) implementiert. Dies ist insbesondere für die firmenorientierte Version von EffSync kritisch, um die Infrastruktur gegen Überlastung zu schützen.
```typescript
@Controller("auth")
export class AuthController {
  // some code

  @Throttle({ default: { limit: 3, ttl: 60000 } }) // erlaubt 3 req/60s
  @Post("register")
  register(@Body() CreateUserDto: CreateUserDto) {
    return this.authService.register(CreateUserDto);
  }

  @Throttle({ default: { limit: 3, ttl: 60000 } }) // erlaubt 3 req/60s
  @Post("login")
  login(@Body() LoginDto: LoginDto) {
    return this.authService.login(LoginDto);
  }

  // some code
}
```
Zusätzlich wird der `ThrottlerGuard` global als `APP_GUARD` registriert, sodass alle Routen des Systems einem Basis-Limit von 10 Requests pro 60 Sekunden unterliegen. Kritische Routen wie Login und Register überschreiben diesen Wert mit einem strengeren Limit von 3 Requests pro 60 Sekunden.

- **Anwendungsbereich:** Kritische Routen wie die Registrierung, der Login werden mit strikten Limits versehen.

- **Schutzwirkung:** Effektive Prävention von Brute-Force-Angriffen auf Benutzerkonten sowie Schutz vor Denial-of-Service (DoS)-Szenarien.
