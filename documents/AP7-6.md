# Deployment, Backup- & Restore- Strategie, Monitoring

## 1. Backup- & Restore-Strategien

Die Auswahl der Strategie folgt der Abwägung von **Recovery Point Objective (RPO)** und **Recovery Time Objective (RTO)**.

### Logischer Dump (einfache Lösung)
*   **Technologie:** `pg_dump` + lokal auf selfhosted Servern oder AWS S3-kompatibler Object Storage (z. B. Cloudflare R2).
*   **Backup-Typ:** Full Backup (Logisch).
*   **Restore:** 
    *   Plain-Text (`.sql`): `psql -f backup.sql`
    *   Custom-Format (`-Fc`): `pg_restore -d dbname backup.dump`
*   **Automatisierung:** Bash-Skript via Systemd-Timer; Upload mittels `rclone`.
*   **Risiken:** RPO bis zu 24h; langsamer Restore bei Datenbanken > 50 GB.
*   **Empfehlung:** MVP-Phase, Schüler & Studenten.
*   *Quelle:* [PostgreSQL Docs – SQL Dump](https://www.postgresql.org/docs/current/backup-dump.html)

### 1.2 Managed Cloud Backups (Standard für Firmen)
*   **Technologie:** Managed DB Services (z. B. DigitalOcean, AWS RDS).
*   **Backup-Typ:** Kontinuierliche Snapshots + Point-in-Time Recovery (PITR).
*   **Restore:** Sekundengenaues Rollback über Provider-Dashboard.
*   **Automatisierung:** Vollständig automatisiert (Zero Ops).
*   **Risiken:** Höhere monatliche Fixkosten; Vendor Lock-in.
*   **Empfehlung:** Startups und produktive Business-Apps.
*   *Quelle:* [AWS RDS Backup Features](https://aws.amazon.com/rds/features/backup/)

### 1.3 Physische WAL (Write-Ahead Logging) Archivierung (Profi-Lösung)
*   **Technologie:** **WAL-G** (für Cloud-Native) oder **Barman** (für On-Premise).
*   **Backup-Typ:** Base-Backup + kontinuierliches Streaming der Write-Ahead-Logs (WAL).
*   **Restore:** Einspielen des Base-Backups und Replay der WAL-Segmente.
*   **Automatisierung:** WAL-G läuft als Sidecar-Prozess.
*   **Risiken:** Hohe Komplexität in der Initialkonfiguration.
*   **Empfehlung:** Hochverfügbare Systeme mit minimalem RPO.
*   *Quelle:* [WAL-G GitHub](https://github.com/wal-g/wal-g) | [PostgreSQL Continuous Archiving](https://www.postgresql.org/docs/current/continuous-archiving.html)

## 2. Deployment-Methoden

### 2.1 Docker Compose auf VPS (Virtual Private Server) (selber Hosten)
*   **Infrastruktur:** VPS (z. B. Hetzner Cloud, oder Heimserver).
*   **Komponenten:** Docker Compose, Nginx (Reverse Proxy), Certbot (SSL).
*   **Vorteile:** Maximale Kontrolle, extrem kosteneffizient (~5–10 €/Monat fuer Strom).
*   **Nachteile:** Manuelle OS-Wartung erforderlich.
*   **Bewertung:** Beste Wahl für EffSync zum Go-Live.
*   *Quelle:* [Docker Compose Best Practices](https://docs.docker.com/compose/)

### 2.2 PaaS (Railway / Render)
*   **Infrastruktur:** Platform-as-a-Service.
*   **Vorteile:** Automatisches CI/CD, integriertes SSL, "Zero Configuration".
*   **Kosten:** Usage-based (Start ab ~5-30 $/Monat plus mehrkosten wenn der Kredit aufgebraucht ist).
*   **Bewertung:** Ideal für schnelle Iterationszyklen ohne Infrastruktur-Aufwand.
*   *Quelle:* [Railway Docs](https://docs.railway.app/)

### 2.3 Kubernetes (K3s / Managed K8s)
*   **Vorteile:** Self-healing, horizontale Skalierbarkeit.
*   **Nachteile:** Massive Lernkurve; hoher Kostenfaktor (~60+ €/Monat).
*   **Bewertung:** Erst bei massiver Skalierung (tausende parallele User) sinnvoll.

## 3. Monitoring & Sicherheit

### 3.1 Monitoring-Konzept
*   **Werkzeug:** **Uptime Kuma** (leichtgewichtig & self-hosted).
*   **Checks:** 
    *   HTTP-Check auf `/api/health` (via `@nestjs/terminus`).
    *   TCP-Check auf PostgreSQL Port 5432.
    *   "Push-Monitor" für Backups (Dead Man's Snitch Prinzip).
*   **Alerting:** Benachrichtigung via E-Mail oder Webhook.
*   *Quelle:* [Uptime Kuma Repository](https://github.com/louislam/uptime-kuma), [Uptime Kuma website](https://uptimekuma.org/)

```typescript
app.get('/api/health', (req, res) => {
  res.status(200).json({
    status: 'ok',
    uptime: process.uptime(),
    timestamp: Date.now()
  });
});
```

### 3.2 Sicherheit (Hardening)
*   **DB:** Kein externer Zugriff; App nutzt eingeschränkte DB-Rolle (Non-Superuser).
*   **Secrets:** Injektion via Umgebungsvariablen; kein `.env` im Repository.
*   **Traffic:** TLS 1.3, HSTS-Header und HTTPS-Erzwingung via Nginx.
