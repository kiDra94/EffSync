## 2. Die Testpyramide – effsync

```
          ┌───────────────────────────────┐
          │       E2E-Tests (Cypress)     │  ← wenige, kritische User-Flows
          │   Frontend: Vue 3 / effsync   │
          └───────────────────────────────┘
        ┌─────────────────────────────────────┐
        │     API / Integrationstests         │  ← alle HTTP-Endpunkte
        │   Backend: NestJS + Supertest       │
        └─────────────────────────────────────┘
    ┌───────────────────────────────────────────────┐
    │              Unit-Tests                       │  ← Basis / größte Menge
    │  Frontend: Vitest   |   Backend: Jest         │
    └───────────────────────────────────────────────┘
```

**Grundprinzip:** Je weiter unten in der Pyramide, desto mehr Tests, desto schneller, desto isolierter.

## 4. Coverage-Strategie

Es existiert kein verbindlich vorgeschriebener Coverage-Prozentwert in der Softwareentwicklung. Selbst Google hält in seinen internen Engineering-Richtlinien fest:

> *„Although there is no 'ideal code coverage number,' at Google we offer the general guidelines of 60% as 'acceptable', 75% as 'commendable' and 90% as 'exemplary.' However we like to stay away from broad top-down mandates and encourage every team to select the value that makes sense for their business needs."*
> — Google Engineering Practices ([testing.googleblog.com](https://testing.googleblog.com/2020/08/code-coverage-best-practices.html))

Da auch der Betreuer keine konkreten Vorgaben gemacht hat, orientiert sich die Strategie an der **Art der Komponente** und dem **Risikopotenzial** bei Fehlfunktion – im Sinne der Google-Empfehlung, den sinnvollen Wert projektspezifisch zu wählen:

- **Kritische Business-Logik (Services, Guards, Auth):** Angestrebte Abdeckung ca. 75–90% („exemplary" nach Google). Diese Bereiche enthalten sicherheitsrelevante und kernfunktionale Logik, bei der ungetestete Code-Pfade ein hohes Fehlerrisiko darstellen.
- **Controller, DTOs, Pipes:** Kein fixer Prozentwert. Validierung erfolgt indirekt über die API-Tests – entscheidend ist, dass alle Endpunkte korrekt antworten, nicht die Zeilen-Coverage.
- **API / Integrationstests:** Auf Integrationsebene wird keine zeilenbasierte Code-Coverage gemessen. Stattdessen gilt das Kriterium der **Endpunkt-Vollständigkeit**:
Jeder HTTP-Endpunkt wird mit mindestens einem Happy-Path-Request (erwarteter 2xx-Response) sowie allen relevanten Fehlerpfaden (4xx: Validierungsfehler, fehlende Authentifizierung, unzureichende Autorisierung, nicht gefundene Ressourcen) abgedeckt. Supertest führt dabei vollständige HTTP-Zyklen gegen den laufenden NestJS-Server aus – inklusive Middleware, Guards, Pipes und Datenbankinteraktion – womit eine isolierte Unit-Coverage auf dieser Ebene methodisch nicht aussagekräftig wäre.
- **E2E-Tests (Cypress):** Code-Coverage ist auf E2E-Ebene nicht aussagekräftig und wird nicht gemessen. Die Abdeckung wird durch die **Vollständigkeit der getesteten User-Flows** bewertet.

## 5. Ebene 1 – Unit-Tests

### 5.1 Backend (NestJS / Jest)

Unit-Tests testen einzelne Klassen isoliert, alle Abhängigkeiten (wie Prisma) werden gemockt (`jest.mock`, `@nestjs/testing`).

#### Bereiche mit hoher Priorität (Ziel: ≥ 90%)

| Bereich | Begründung |
|---|---|
| `AuthService` | JWT, bcrypt, Passport-Logik – sicherheitskritisch |
| `JwtAuthGuard`, `LocalAuthGuard` | Zugangskontrolle – sicherheitskritisch |
| `TaskService` / `ProjectService` | Kernlogik der Diplomarbeit |
| Custom Pipes & Validators | Eingabe-Validierung für alle Endpunkte |

#### Bereiche mit mittlerer Priorität (Ziel: ≥ 75%)

| Bereich | Begründung |
|---|---|
| `UserService` | CRUD-Operationen, aber weniger komplex |
| `PermissionService` | Wichtig, aber oft durch API-Tests mitabgedeckt |
| DTO-Klassen (`class-validator`) | Werden indirekt durch API-Tests getestet |

#### Bereiche ohne Coverage-Ziel

- `main.ts`, `app.module.ts` – Bootstrap-Code, kein Business-Value
- Prisma-Schema-Dateien – keine Logik
- Konfigurationsmodule – werden durch Integration abgedeckt

### 5.2 Frontend (Vue 3 / Vitest)

Unit-Tests für Composables, Pinia Stores und einzelne Komponenten-Logik.

#### Bereiche mit hoher Priorität (Ziel: ≥ 90%)

| Bereich | Begründung |
|---|---|
| Pinia Auth-Store | Login-State, Token-Handling |
| Pinia Task-Store | Kernzustand der Anwendung |
| HTTP-Utility-Functions (Axios-Wrapper) | Basis aller API-Aufrufe |

#### Bereiche mit mittlerer Priorität (Ziel: ≥ 75%)

| Bereich | Begründung |
|---|---|
| Routen-Guards (Vue Router) | Auth-Redirect-Logik |
| Wiederverwendbare Komponenten (z.B. Modal, Form) | Werden auch durch E2E mitgetestet |

#### Bereiche ohne Coverage-Ziel

- Reine CSS/Layout-Komponenten (keine Logik)
- `App.vue` / Router-Setup – abgedeckt durch E2E

## 6. Ebene 2 – API / Integrationstests

API-Tests laufen gegen den laufenden NestJS-Server und testen vollständige HTTP-Anfragen mit Supertest. Die Datenbank wird **nicht gemockt**, um echte Datenbankinteraktionen zu validieren.

### 6.1 Test-Datenbank-Setup & Determinismus

Um deterministische und isolierte Testbedingungen zu garantieren, wird vor den API-Testläufen die Datenbank vollständig zurückgesetzt und neu befüllt. Dies verhindert *State Leakage*, bei dem ein Testlauf die Daten für nachfolgende Tests manipuliert.

Hierzu wird die `test-seed.ts` verwendet, welche eine vordefinierte Struktur (1 Klasse, 4 Tasks, Chats, Notifications, etc.) erzeugt.

#### package.json Skripte

```json
"scripts": {
  "test:seed": "ts-node test-seed.ts",
  "test:db:reset": "prisma migrate reset --force && npm run test:seed",
  "test:e2e": "npm run test:db:reset && jest --config ./test/jest-e2e.json"
}
```

#### Jest E2E Konfiguration (test/jest-e2e.json)

Um den DB-Reset vollautomatisch vor dem Start aller E2E-Tests anzustoßen, wird ein `globalSetup` registriert.

### 6.2 Strategie pro Endpunkt

Für jeden Endpunkt wird mindestens getestet:
- **Happy Path** (200/201) – korrekte Eingabe, erwarteter Response
- **Error Path** (400/401/403/404) – fehlende Auth, ungültige Daten, nicht gefundene Ressourcen

### 6.3 Endpunkt-Prioritäten

#### 🔴 Kritisch – zwingend testen (Kern der Diplomarbeit)

| Endpunkt | Methode | Priorität | Warum |
|---|---|---|---|
| `/api/auth/register` | POST | Kritisch | Öffentlich + Validierung + Duplikat-Check (409) |
| `/api/auth/login` | POST | Kritisch | JWT-Ausgabe, sicherheitskritisch |
| `/api/auth/logout` | POST | Kritisch | Token-Invalidierung |
| `/api/tasks` | POST | Kritisch | Kernfeature, Validierung |
| `/api/tasks` | GET | Kritisch | Filter + Sortierung nach Priorität/Status |
| `/api/tasks/:id` | GET | Kritisch | Detail-Abruf |
| `/api/tasks/:id` | PATCH | Kritisch | Teil-Aktualisierung (Status, Deadline) |
| `/api/tasks/:id` | DELETE | Kritisch | Delete-Guard: nur wenn keine Subtasks vorhanden |

#### 🟡 Wichtig – testen wenn Zeit vorhanden

| Endpunkt | Methode | Warum |
|---|---|---|
| `/api/users/profile` | GET / PUT | Auth-abhängig, Profil ist Teil aller Features |
| `/api/documents` | POST | File-Upload, Berechtigungsprüfung |
| `/api/documents/:id` | GET | Berechtigungsprüfung beim Download ist fehleranfällig |
| `/api/notes` | GET / POST | Sharing-Logik |
| `/api/notes/:id` | PATCH / DELETE | Ownership-Check |
| `/api/notifications` | GET | Einfach, aber schnell geschrieben |
| `/api/notifications/:id` | PATCH | Gelesen-Markierung |

## 7. Ebene 3 – E2E-Tests

E2E-Tests laufen im Browser über **Cypress** und testen vollständige User-Flows aus Nutzerperspektive.

### Strategie

E2E-Tests sind **Black-Box-Tests** – kein direkter Zugriff auf Code-Coverage. Die Abdeckung wird durch **Flow-Vollständigkeit** bewertet, nicht durch %-Werte.

### Zu testende User-Flows (Pflicht)

| Flow | Beschreibung | Priorität |
|---|---|---|
| Login-Flow (Erfolg) | User gibt Credentials ein, wird weitergeleitet | Kritisch |
| Login-Flow (Fehler) | Falsche Credentials → Fehlermeldung sichtbar | Kritisch |
| Task erstellen | Formular ausfüllen → Task erscheint in der Liste | Kritisch |
| Task-Status ändern | Task anklicken → Status wechseln → gespeichert | Hoch |
| Logout | User klickt Logout → wird zur Login-Seite geleitet | Kritisch |
| Geschützte Route | Direktaufruf ohne Auth → Redirect zu Login | Hoch |

### Zu testende User-Flows (Optional / bei Zeit)

| Flow | Beschreibung |
|---|---|
| Task bearbeiten | Name/Beschreibung ändern und speichern |
| Task löschen | Task löschen → verschwindet aus Liste |
| Subtask erstellen | Subtask unter bestehendem Task anlegen |
| Profil anzeigen | Eingeloggter User sieht eigene Daten |

## 8. Zusammenfassung Coverage-Ziele

| Bereich | Tool | Ziel |
|---|---|---|
| Backend Services (Auth, Task, Permission) | Jest | ≥ 90% |
| Backend Controllers, DTOs, Pipes | Jest | ≥ 75% |
| Frontend Pinia Stores & Composables | Vitest | ≥ 90% |
| Frontend Komponenten-Logik | Vitest | ≥ 75% |
| API-Endpunkte (kritisch) | Supertest | Endpunkte mit Happy + Error Path |
| API-Endpunkte (wichtig) | Supertest | Endpunkte mit Happy Path |
| E2E User-Flows | Cypress | kritische Flows (verhaltensbasiert) |
| Bootstrap / Konfig-Code | – | kein Ziel |

***

## 9. Implementierungsreihenfolge

1. **Unit-Tests Backend** – Auth-Service und Guards zuerst (sicherheitskritisch)
2. **Unit-Tests Frontend** – Pinia Stores (Auth + Task)
3. **API-Tests kritisch** – alle definierten Endpunkte mit Happy + Error Paths
4. **API-Tests wichtig** – nach Zeitverfügbarkeit
5. **E2E-Tests** – die kritischen User-Flows in Cypress
6. **Coverage-Report generieren** und in Diplomarbeit dokumentieren
